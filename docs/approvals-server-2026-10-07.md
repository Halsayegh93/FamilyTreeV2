# الموافقات من السيرفر — تصميم أ-٣ (٢٠٢٦-١٠-٠٧، بموافقة المالك)

**المشكلة (أ-٣ في `security-audit-2026-10-04.md`):** قرار «قبول/رفض» طلب المراجعة يُنفَّذ في التطبيق نفسه: يعيد فحص «معلّق»، يكتب التعديل على الملف، يرسل الإشعارات، ثم يغلق الطلب — عدة طلبات شبكة منفصلة. النتيجة: كتابة نصف ناقصة إذا انقطع الاتصال، موافقتان متزامنتان تطبّقان مرتين، وكتابة مباشرة على `profiles`/`news` يجب أن تبقى مفتوحة للتطبيقات.

**الحل:** دالة سيرفر واحدة `decide_admin_request` تتحقق من الصلاحية، تقفل الطلب، تطبّق **نفس** ما يكتبه الآيفون اليوم، تكتب الإشعارات نفسها، وتغلق الطلب — كلها في معاملة واحدة. الترحيل: `supabase/migrations/20261007170000_decide_admin_request.sql`، التراجع في `supabase/rollback/`، التجربة `supabase/tests/family_links/decide_admin_request.test.mjs`.

**الحالة (٢٠٢٦-١٠-٠٧):** مطبّقة على الحي — `md5(prosrc) = 6446a049838773ec073e9f5a46691c96` (مطابق للملف)، تنفيذ لـ `authenticated` فقط. التجربة المحلية ١٧٤/١٧٤ (كل نوع قبول + رفض بالكتابات والإشعارات، الدور الخطأ، المعالَج سابقاً، الحمولة الفاسدة، الذرّية، الحراس، التراجع). تجربة جافة على الحي داخل معاملة أُلغيت بصفوف واقعية (عضو، ابن معلّق، خبر، ٨ طلبات عبر حارس الإدراج الحي، قرارات بمدير ومشرف حقيقيين، الدفع معطّل داخلها): كل النتائج كما المتوقع. الآيفون يستدعيها؛ الأندرويد والموقع لم يُغيَّرا.

## من يقرّر (بلا تغيير)
`can_handle_admin_request(type)` — نفس شرط سياسة `admin_requests_update_by_scope` اليوم:

| الدور | الأنواع |
|---|---|
| المالك، المدير | الكل |
| المراقب | كل الأنواع عدا البلاغات (`news_report`، `content_report`) |
| المشرف | البلاغات ورسائل التواصل فقط |
| العضو، المعلّق، المجمّد | لا شيء |

وطلبك أنت (أنت مقدّمه أو صاحبه `member_id`) يعالجه غيرك — إلا المالك (كالسياسة نفسها، بـ `auth.uid()` و`current_profile_id()` معاً).

## ما يكتبه الآيفون اليوم لكل نوع (`ViewModels/Admin/AdminRequestViewModel.swift`)
«إشعار صاحب الطلب» = `sendNotification` (صف في `notifications` لـ `requester_id`) — **يُرسل فقط إذا كان المتّخذ مالكاً أو مديراً** (حارس `isAdmin` في `sendNotification`؛ قرارات المراقب/المشرف لا تُبلَّغ — ج-٤). «إعلان الإدارة» = `notifyAdminsWithPush`: صف `target_member_id = NULL` (يوزّعه `fanout_broadcast_notification` نسخةً لكل إداري) + دفع خارجي عبر `push-admins`.

## الدالة
```sql
decide_admin_request(p_request_id uuid, p_decision text /* approve | reject */,
                     p_reason text default null, p_overrides jsonb default null) returns jsonb
-- SECURITY DEFINER, search_path = public، تنفيذ لـ authenticated فقط
```
1. متصل بدخول (`not_authenticated`)، القرار `approve`/`reject` (`bad_decision`).
2. `select … for update` على الطلب (`request_not_found`)، النوع من التسعة أعلاه (`unsupported_type`).
3. `can_handle_admin_request(type)` (`not_allowed`)، ليس طلبك إلا للمالك (`own_request`)، الحالة «معلّق» (`already_handled`).
4. التطبيق كما في الجدول. حمولة لا تُطبَّق (معرّف ليس uuid، تاريخ غير صالح، اسم/رقم/رابط فارغ في الأنواع التي يرفضها التطبيق) → `bad_payload`، رقم مستخدم → `phone_in_use`؛ وأي خطأ من الحراس (`family_links_protected`، `owner_protected`…) يُرجع كما هو. أي خطأ = لا شيء يُكتب والطلب يبقى معلّقاً.
5. إغلاق الطلب، ثم الإشعارات أعلاه (صفوف `notifications` — الدفع يخرج من المشغّل `trg_push_on_notification` كما اليوم).
6. `p_overrides`: `{"silent": true}` فقط، ولقبول `child_add` فقط (القبول الجماعي بلا إشعارات كما اليوم).

الأخطاء: `errcode` 42501/P0001/P0002/22023 و`hint` = اسم الخطأ (يعرضه التطبيق بالعربية). النتيجة:
```json
{ "ok": true, "request_id": "…", "request_type": "tree_edit", "status": "approved", "action": "deceased",
  "requester_notified": true,
  "admin_push": { "title": "…", "body": "…", "kind": "tree_edit" },        // للتطبيق: push-admins كما اليوم
  "death_announcement": { "member_id": "…", "name": "…", "is_female": false, "death_date": null },
  "storage_cleanup": { "bucket": "avatars", "paths": ["photo_suggestion_…jpg"] },
  "new_member_id": "…" }
```

## ما يبقى في التطبيق ولماذا
- **الدفع الخارجي للإدارة `push-admins`**: الدالة الطرفية تتحقق بجلسة المستخدم، والسيرفر لا يستدعيها؛ التطبيق يرسل `admin_push` المرتجع كما يفعل اليوم.
- **حذف ملف اقتراح الصورة**: الحذف المباشر من `storage.objects` ممنوع (`storage.protect_delete`) — التطبيق يحذف `storage_cleanup` عبر Storage API بعد نجاح الرفض.
- **مربّع «إعلان وفاة»**: واجهة — التطبيق يعرضه من `death_announcement`.
- **طلبات الانضمام/الربط (`join_request`، `link_request`) ورسائل التواصل — لم تُنقل الآن.** ليست قراراً على صف طلب: الموافقة تفعيل ملف من أربعة مداخل مختلفة (`activateAccount` بشرط الأب، `bulkApproveJoinRequests`، رقم + تفعيل، «ربط» عبر `merge_member_into_tree` وهو دالة سيرفر بحراس أصلاً)، والرفض حذف الملف. ما تكتبه محمي بالسيرفر اليوم: `prevent_role_self_promotion` (الإدارة فقط، من «معلّق» إلى عضو مفعّل)، سياسة الحذف (المالك والمدير) وحراس الحذف. نقلها يغيّر أربع شاشات ويحتاج دالة ثانية — أخطر من فائدته الآن. رسائل التواصل: «تمت المعالجة» تغيير حالة فقط.
- `edit_request` (نوع قديم بلا مصدر، صف واحد معلّق): لا يعالجه أي تطبيق → `unsupported_type`.

## فروق مقصودة عن اليوم (صغيرة)
- **ذرّية**: كل شيء أو لا شيء؛ موافقتان متزامنتان → الثانية `already_handled` بدل تطبيق مزدوج.
- **نصوص الإشعارات بالعربية** (كل إشعارات السيرفر عربية؛ كانت بلغة واجهة المتّخذ).
- المشرف لم يعد يطبّق كتابة طلب شجرة ثم يفشل الإغلاق (الأزرار مخفية عنه أصلاً) — يُرفض قبل أي كتابة.
- رفض اقتراح الصورة يحذف ملفات `photo_suggestion_*` فقط (كان يحذف أي مسار في الرابط — أ-٣).
- قبول `content_report` لا يحذف خبراً (كان يحاول `news.id = new_value`؛ الحارس يمنع بلاغ محتوى يشير لخبر منذ ١٠-٠٤).
- رقم مستخدم في «تغيير الرقم» → رسالة `phone_in_use` بدل لا شيء صامت؛ والفحص يشمل الأرقام المخفية.

## باقٍ لقرار المالك (لم يُغيَّر — «بلا سلوك جديد»)
1. إبلاغ صاحب الطلب بقرارات المراقب/المشرف (ج-٤) — سطر واحد في الدالة (`my_role in ('owner','admin')`).
2. رفض المراقب لـ«إضافة ابن» لا يحذف الابن المعلّق (كاليوم).
3. حراس على المحتوى نفسه (أ-٣ «باقٍ»): رقم على عضو لم يدخل (استيلاء عبر adopt)، وفاة أحد الإدارة — الآن في مكان واحد يسهل إضافتها.

## الأندرويد والموقع
ما زالا يطبّقان الموافقة بأنفسهما (أندرويد `core/data/admin_requests.dart`، `admin_review_requests_screen.dart`؛ الموقع `lib/profile-edit-approval.ts`). المطلوب: استدعاء `rpc('decide_admin_request', {p_request_id, p_decision, p_reason})` بدل الكتابة، وإرسال `admin_push` إلى `push-admins`، وحذف `storage_cleanup`، وعرض `death_announcement`.

## الإقفال اللاحق (بعد تحديث الكل — لا يُطبَّق الآن)
**متى:** بعد نشر نسخة آيفون وأندرويد (والموقع) تستدعي الدالة، ورفع `app_settings.ios_min_build` / `android_min_build` لرقمي بنائهما (النسخ الأقدم تنقفل بشاشة «حدّث التطبيق»)، ومراقبة أسبوع أن لا كتابة مباشرة على `admin_requests.status` من التطبيقات.

| ما يُشدَّد | اليوم | بعد |
|---|---|---|
| `admin_requests_update_by_scope` (UPDATE) | الإدارة تغيّر `status` لأي طلب في مجالها | يبقى لـ `contact_message` (تمت المعالجة/الرد) و`join_request`/`link_request` فقط؛ باقي الأنواع عبر الدالة |
| `profiles_update_self_or_moderator` (UPDATE) | الإدارة تعدّل أي عمود لأي عضو | لا يُسحب (تعديل الإدارة المباشر يحتاجه) — يكفي ما فوقه، لأن الطلب لا يُغلق إلا بالدالة |
| `news_delete_owner_or_moderator` | يبقى | يبقى (حذف الخبر من شاشته) |
| حذف `admin_requests` (`admin_requests_delete_by_scope`) | الإدارة تحذف أي طلب في مجالها | للمالك والمدير فقط (حذف السجل نهائياً) |
| `notifications_insert_moderator_or_self_scope` | المراقب/المشرف يكتبون إشعاراً لأي عضو | يُراجع بعد نقل الانضمام والمحتوى (الإعلانات ما زالت من التطبيق) |

المرحلة الثانية (اختيارية): دالة ثانية للانضمام/الربط (`decide_join_request`) ثم سحب UPDATE على `admin_requests` من التطبيقات كلياً.
